# The default piano against FluidSynth: measured

Results for
[Acceptance: the default piano against FluidSynth](../../issues/07-acceptance-the-default-piano-against-fluidsynth.md),
2026-11-24. Throwaway, outside the build. The ticket's comments hold the setup, the causes and
the follow-ups; this file holds the numbers.

- **Renderers.** The soundfont node, natively (MSVC, CMake's Release flags), at `22c5bd8`
  plus this harness, and FluidSynth 2.6.3's Windows x64 release, with reverb and chorus off.
  Both play bank 0, program 0 of the full `FluidR3_GM.sf2` at 44.1 and 48 kHz.
- **Produced by** [`run.ps1`](run.ps1), which writes every comparison below with
  [`PROTOTYPE_compare.py`](PROTOTYPE_compare.py). The renders are deterministic: three runs
  gave the same numbers.
- **Variants.** "As built" is the node on the tree. The others rebuild it from a patched copy
  of the sources (`patches/`): "96 dB envelope" makes decay and release fall 96 dB over their
  stage's time, as FluidSynth's do, instead of 100; "no velocity-to-cutoff" removes the
  default velocity-to-cutoff modulator, which FluidSynth zeroes; "both" does both. "FluidSynth
  with the node's curve" plays a copy of the file whose piano carries a file modulator with
  the node's velocity-to-cutoff curve ([`PROTOTYPE_add_modulator.py`](PROTOTYPE_add_modulator.py)).
- **Thresholds.** Onset within FluidSynth's 64-frame block; pitch within ±1 cent; every 10 ms
  RMS window within ±1 dB while FluidSynth's is within 60 dB of its peak, after one global
  offset. "Worst window" is each note's largest level error after the offset; the column
  gives the range of those over the notes, at both rates.
